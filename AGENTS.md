## Project Goal

This project tests whether a model can learn to reason more efficiently by training on corrected local transitions extracted from reasoning traces generated by the current model version itself: `question + useful reasoning prefix → next useful reasoning step`. Code runs as uv-managed Python utilities, a CLI, and Hugging Face Jobs scripts. Serious dataset creation and training are designed for Hugging Face cloud infrastructure; local execution is for tests, config checks, dry runs, and script validation.

## Data Creation — Detailed Walkthrough

### The core idea

G generates its own reasoning trace. D finds the first step in that trace that is genuinely redundant — a step that contributes no new computation. We keep everything before the removed step as the "useful prefix", skip the removed step(s), and use the very next step as the training target. The resulting row teaches the model: *given this question and this useful prefix, jump directly to this concrete step — do not emit the filler in between.*

### Step-by-step for one question

**1. Load config and questions**

`dataset_builder_config.py` reads a YAML such as `configs/data/dataset_builder_gsm8k_100_gemma4.yaml`. That config specifies which model is G (e.g. `google/gemma-4-E2B-it`), which model is D (e.g. `gemini-2.0-flash-lite`), which prompt file to use, where the questions come from, and where to publish.

`question_source.py` reads the questions. For a local `.txt` file it reads one question per non-empty line. For `hf_dataset` it calls `datasets.load_dataset` and extracts the configured field.

**2. Build context for the first depth**

For the first iteration of each question, `accepted_units = []` (empty). The context passed to G is:

```
Question:
<question text>
```

At subsequent depths, the context grows with the accepted units so far:

```
Question:
<question text>
<accepted unit 0>
<accepted unit 1>
...
```

**3. G generates a reasoning trace**

`model_clients.py` calls G (Transformers or Gemini) with the context and an instruction to continue reasoning. G returns a raw text string — a multi-step reasoning trace such as:

```
1. We need to find the total cost.
2. Each item costs $5, and there are 4 items.
3. 4 x 5 = 20.
4. The total cost is $20.
```

**4. Split into units**

`reasoning_units.py` → `split_reasoning_units(trace.text)` splits the raw string into a `list[str]`. The default strategy (`numbered_or_lines`) detects numbered steps (`1.`, `2.`, ...) or falls back to splitting on line breaks. Each element is one reasoning unit.

```python
units = [
    "We need to find the total cost.",            # index 0
    "Each item costs $5, and there are 4 items.", # index 1
    "4 x 5 = 20.",                               # index 2
    "The total cost is $20.",                     # index 3
]
```

**5. D decides which span to remove**

`model_clients.py` fills the prompt template from `prompts/<prompt_version>.txt` with `question`, `context`, and the numbered units, then calls D. D returns JSON:

```json
{
  "has_removal": true,
  "removed_start_index": 0,
  "removed_end_index": 0,
  "reason": "Step 0 only restates the goal without computing anything.",
  "can_continue_after_skip": true
}
```

`parse_json_pruning_decision` converts this to a `PruningDecision` dataclass. `valid_span_for(len(units))` checks that: `has_removal` and `can_continue_after_skip` are both `True`, the indices are in range, and `removed_end_index + 1` is a valid index (there must be a concrete step after the removed span).

The D prompt (`conservative-skip-v1`) enforces one hard rule: **`target_y` (the step immediately after the removed span) must contain concrete computation or deduction — not a goal statement, intent, or meta-commentary.** If the step after the removed span would itself be non-computational, D must not mark the span as removable.

**6. Build the canonical row**

`data.py` → `build_pruning_transition_row(...)` constructs:

```python
{
  "id": "pt-<sha256[:16]>",               # stable hash of (round_id, question, depth, span)
  "question": "<original question>",
  "original_trace": "<full G trace text>",
  "input_x": "Question:\n<question>\n\nUseful reasoning prefix:\n<units before removed span>",
  "target_y": "<units[removed_end_index + 1]>",   # first useful step after the skip
  "pruning_depth": 0,                              # which iteration of the loop this came from
  "metadata": {
    "source_model": "google/gemma-4-E2B-it",
    "decision_model": "gemini-2.0-flash-lite",
    "removed_span": "<the removed unit text>",
    "removed_start_index": 0,
    "removed_end_index": 0,
    "decision_reason": "Step 0 only restates the goal...",
    "round_id": "gsm8k-100-gemma4-r1",
    ...
  }
}
```

**`input_x`** is what the model sees at inference time — the question plus every accepted reasoning step so far.
**`target_y`** is what the model should generate next — the first concrete step after the skipped span.

For the example above (remove index 0, target is index 1):
- `input_x` prefix = `(empty)` (nothing accepted yet)
- `target_y` = `"Each item costs $5, and there are 4 items."`

**7. Update context and repeat**

After building the row, `pt_dataset_builder.py` updates `accepted_units`:
- Keep all units *before* the removed span: `units[:removed_start_index]`
- Append the unit *after* the removed span: `units[removed_end_index + 1]`

The loop then repeats at the next depth with this updated context as the new prefix, until `max_pruning_depth` or `max_examples_per_question` is reached, or D finds no valid removal.

**8. Publish to the Hub**

`hf_dataset_publisher.py` → `push_pt_dataset_to_hub(rows, hub_dataset_id)` pushes two configs to the same HF repo:

- **`canonical`** config: the raw canonical rows with `input_x`, `target_y`, `metadata`, etc.
- **`training`** config: the same rows plus `prompt` and `completion` fields added by `data.py` → `transition_row_to_prompt_completion`:

```
prompt     = "{input_x}\n\nContinue with the next useful reasoning step:"
completion = target_y
```

The two configs have different schemas so they are pushed as separate `config_name` values (not separate splits). The training script loads `config_name="training"` and trains on `prompt`/`completion`.

## Building and Running

**Prerequisites:**
- Python 3.11+, `uv` for all environment/dependency/test execution
- HF account + token with write access; W&B API key for training
- Local `.env` containing `HF_TOKEN`, `GEMINI_API_KEY`, `WANDB_API_KEY` — never commit this file

**Local validation:**
```bash
uv run pytest
uv run python scripts/reasoning_pruning_cli.py build-dataset \
    --config configs/data/dataset_builder_gsm8k_100_gemma4.yaml --dry-run
uv run python -m py_compile scripts/create_dataset_gemma4_job.py
```

**Dataset creation (cloud):**
Submit `scripts/create_dataset_gemma4_job.py` to HF Jobs with `HF_TOKEN` and `GEMINI_API_KEY` secrets. The script runs the PT loop over 100 GSM8K questions and pushes to `avreymi/reasoning-pruning-pt-gsm8k-100-gemma4-r1`.

**D-prompt iteration (local):**
```bash
uv run python scripts/generate_traces.py   # writes data/traces/*.jsonl
uv run python scripts/replay_decisions.py  # runs D on cached traces with any prompts/*.txt
```

**Training (cloud):**
Submit `scripts/train_pt_dataset_job.py` to HF Jobs with `HF_TOKEN` and `WANDB_API_KEY` secrets; set `TRAINING_CONFIG=configs/train/training_gemma4_gsm8k_100.yaml`.
